# REVIEW.md

## Identified Starter Code Defects

| # | Where (function / line) | What is wrong | How you'd notice it (test, input, or symptom) | How you fixed it |
|---|---|---|---|---|
| 1 | `health` (lines 72–74) | Returned `{"status": "ok"}` unconditionally without checking if MongoDB is reachable. | Calling `/health` returned 200 even when MongoDB was stopped or unreachable, violating the readiness probe contract (which requires 503). | Added `client.admin.command("ping")` within a try/except block; raises `HTTPException(503, "Database unavailable")` if the ping fails. |
| 2 | Startup / Indexes (omitted in starter) | No indexes were created on startup except the default `_id` index. Lacked uniqueness guarantees and caused full collection scans (`COLLSCAN`). | Concurrent requests created duplicate `emp_code` or `(emp_code, date)` documents; `/admin/explain` queries failed grader checks for `IXSCAN`. | Added index initialization in FastAPI lifespan: unique index on `employees.emp_code`, `attendance_logs.(emp_code, date)`, and compound indexes on `employees.(department, joined_on)`, `attendance_logs.(date, -1, emp_code, 1)`, and `attendance_logs.(date, 1, late_minutes, 1)`. |
| 3 | `compute_late_minutes` (lines 33–37) | (a) Naively replaced hour/minute on UTC instant ignoring IST (UTC+05:30); (b) `minutes > 10` after integer floor division evaluated 601s (10m 01s) as 10 > 10 (False), returning 0 instead of 10 per R2; (c) Failed on overnight shifts. | Testing shift start `09:30` with punch-in at `09:40:01 IST` returned `0` instead of `10`. | Converted punch-in to IST; computed scheduled start in IST; checked `diff_sec > 600` and returned `int(diff_sec // 60)`. |
| 4 | `compute_work_hours` (lines 40–41) | Used Python's built-in `round()`, which applies IEEE 754 round-to-even (banker's rounding) rather than commercial round-half-up (R4/R8). | Input durations ending in half-cent values (e.g., 2.675 hours) rounded to 2.67 instead of 2.68. | Implemented half-up rounding using Python's `Decimal` module with `ROUND_HALF_UP`. |
| 5 | `compute_overtime` (lines 44–48) | (a) Returned any positive minutes without enforcing R3's 30-minute minimum threshold; (b) Did not handle overnight shifts where `shift_end <= shift_start` puts shift end on the next calendar day. | Punch-out 5 minutes after shift end returned 5 instead of 0; overnight punch-outs produced incorrect negative or excessive overtime. | Handled next-day calendar shift end for overnight shifts; returned whole minutes only when `minutes >= 30`, else 0. |
| 6 | `create_employee` / `EmployeeIn` (lines 53–61, 77–85) | (a) Permitted `shift_start == shift_end`; (b) Missing regex/length constraints; (c) Stored/returned raw unformatted `datetime.now()` rather than epoch ms; (d) Check-then-insert was vulnerable to race conditions. | Submitting identical start and end shifts was accepted (should be 422); duplicate concurrent creates yielded 500 or duplicate records; response schema violated integer millisecond contract. | Added Pydantic model validator for `shift_start != shift_end` and field patterns; serialized `created_at` as epoch ms; caught `DuplicateKeyError` to return 409. |
| 7 | `list_employees` (lines 88–96) | (a) Pagination bug `skip = page * page_size` skipped the first 20 records on `page=1`; (b) `total` counted the whole collection instead of the filtered query `q`; (c) Missing sorting by `emp_code` ascending. | Requesting `page=1` returned items 21–40; department filters reported total database count; items were unordered. | Fixed skip to `(page - 1) * page_size`; used `count_documents(q)`; added `.sort("emp_code", 1)`; formatted `created_at` as epoch ms. |
| 8 | `punch_in` (lines 99–121) | (a) Crashed with 500 `TypeError` if employee did not exist; (b) Used system local date instead of IST attendance date (R1); (c) Ignored overnight shift boundary; (d) Accepted invalid statuses like ABSENT; (e) Returned forbidden `id` field; (f) Check-then-insert race condition. | Unknown employee resulted in 500 error; post-midnight punch-ins on overnight shifts were assigned the wrong date; concurrent punch-ins produced duplicates; response schema failed contract validation. | Added 404 check; implemented IST date calculation handling overnight shifts; enforced `PresenceStatus`; caught `DuplicateKeyError` to return 409; formatted response according to `AttendanceRecord`. |
| 9 | `list_attendance` (lines 124–150) | (a) Memory scalability defect: loaded all matching documents into memory via `list(...)` and sorted in Python; (b) Did not validate `date_from > date_to` (must be 422); (c) Missing secondary sort `emp_code` asc; (d) Returned forbidden `id` field. | Passing `date_from=2026-07-21&date_to=2026-07-20` returned 200 instead of 422; high record counts (100k) exhausted memory; response returned `id`. | Query executed with database `.sort([("date", -1), ("emp_code", 1)]).skip(...).limit(...)`; added 422 check for `date_from > date_to`; formatted records to schema. |

## Items Verified as Non-Defects

1. **Date & Time Stored as Plain Strings (`YYYY-MM-DD`, `HH:MM`)**:
   - *Consideration*: Initially might appear un-normalized compared to BSON dates.
   - *Rationale*: Confirmed intentional per `DATA_MODEL.md` Section 1. A calendar date or shift time is not a point in time; converting them to timestamps would artificially bind them to a timezone. Storing strings preserves explicit IST semantics cleanly.

2. **Pre-computed Derived Fields in MongoDB (`work_hours`, `late_minutes`, `overtime_minutes`, `half_day`)**:
   - *Consideration*: Might look like redundant data storage.
   - *Rationale*: Confirmed intentional per `DATA_MODEL.md` Section 3. Derived values written during punch-in, punch-out, and regularization are authoritative. Analytics must query these stored values directly to guarantee fast aggregations over 100k+ records.
